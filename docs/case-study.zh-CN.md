# 真实事故完整复盘：DS218+ 双盘 SHR-1，DSM 登录失效与 Btrfs 数据提取（已脱敏）

> **证据范围：** 以下是从现场操作与日志重建的可公开复盘。案例数字属具体设备，不应复制为其他设备的配置；用户、硬盘序列号、IP、域名、路径、个人文件名均不公开。本案例不包含原始私密日志。**相关性不是因果证明**，尤其关于公网登录请求与 OOM 的因果关系。

## 事故背景与最初决策

- 设备：Synology DS218+；两块 4TB 硬盘、SHR-1（RAID1）、**DSM 7.2.2-72806 Update 10**（故障排查及恢复登录时核实）。
- 症状：DSM 登录不可用、SMB 不可用；关键照片无法用常规方式备份。
- 最初最大风险：直接重装 DSM、修复 RAID/Btrfs 或让不同时间点的 RAID 成员自动重同步，可能覆盖尚未取出的数据。
- 取舍：硬盘 B 离线保护；硬盘 A 单独接入 Ubuntu（外置盒 SINGLE 直通），数据分区只读 RAID1/LVM；恢复目标为另一个 ext4 外置盘。

## 第一阶段：确认阵列不等于修复阵列

- 单成员阵列 RAID1，member `1.2`，md 系统标识不同于群晖 `0.90` 系统 RAID；二者不得混淆。
- 数据 RAID 两个成员 Events 分别为 **17119** 和 **16782**，差 **337**。后续证实用户在 DSM 失效**之后**曾仅用硬盘 A 启动过 NAS；因此这段差异可以由启动写入解释，而不是最初故障的直接证据。
- 系统 RAID 超级块、交换 RAID 超级块、数据 RAID 超级块均可识别且 checksum 正确。DSM 系统根分区 ext4 `dumpe2fs` 标记 `clean`，但具有 `needs_recovery` 特性；尚不能由此证明系统完全无误。文件系统报告空闲约 842 MiB，不能简单认定系统根分区耗尽。
- 被拒绝的捷径：`mdadm --create`、`--force` 双盘同步、`--zero-superblock`、`btrfs check --repair`、给原盘执行写入式 fsck。

## 第二阶段：Synology Btrfs 只读恢复

通用 Linux Btrfs 用户态工具在 root item 标志遇到 `0x400000000`；在局部放宽 root bit33/34 后，继续遇到 inode bit30 `0x40000000`。本项目固定官方 `btrfs-progs v6.17.1`，只对 `kernel-shared/tree-checker.c` 应用两处严格匹配的 checker 放宽。**不声明已经实现这些标志在 Synology 中的真实语义，也不修改任何源设备。**

通过只读子卷关系核对，个人 `homes` 的 root 为 **259**，共享 `photo` root 为 **261**。首先成功导出一个数 MB 的 JPEG 和约 193MB 的 MOV，并实际打开。之后分四批导出：

1. 个人 `MobileBackup`（root 259）
2. 个人 `PhotoLibrary`（root 259）
3. 个人 `Moments`（root 259）
4. 共享 `photo`（root 261，整 root）

其中首批 MobileBackup 实测约 **194 GiB、180836 文件，零字节文件 17275（约 9.55%）**。这是重大的**质量未决项**：可能含缩略图/空的附属元数据，也可能包含未成功恢复的原始媒体。不能宣称四批数据已经经过完整校验，更不能只以 `EXIT_CODE=0` 认定“全部已恢复”。后续项目据此加入 `audit` 和零字节媒体清单。

## 第三阶段：从 DSM 日志转向系统/安全故障

- 系统 ext4 在 Ubuntu 上通过 `ro,noload` 可以阅读历史日志；此举不重放 ext4 journal。
- DSM 的 `/var/log/messages` 在 **10 月 22–24 日**反复记录 OOM Killer，涉及数据库、Office/文档、认证及其他服务。
- **10 月 24 日 20:24**，日志记录 `Free swap = 0kB; Total swap = 3221428kB`（约 3.07 GiB）。
- **10 月 24 日 21:45** 的进程列表超过一千条，其中 `synoplugind` **523**、`SYNO.API.Auth_6` **175**、PostgreSQL **126**。这表示大量进程堆积；进程的 RSS 汇总可能包含共享页，不能当作去重物理内存。
- `auth.log` 中 **10 月 22 日 20时**约 **1442** 次 Web 登录失败、21时约 **946** 次；来自多个不同公网 IP，并伴随 `pam_syno_ipblocklist` 数据库超时。符合自动化密码猜测行为，但**没有充分证据确认成功入侵，也尚不能把公网流量证明为唯一 OOM 原因**。
- 另有 SATA `READ FPDMA QUEUED` 链路错误，该段日志紧邻设备拔插；不能直接据此认定磁盘物理损坏。

## 第四阶段：在隔离公网后受控启动 NAS

关闭 NAS 的公网入口（端口转发、公开反向代理等），保留硬盘 B 离线；退出恢复程序、卸载系统 ext4、关闭 LVM/md 的打开引用，将硬盘 A 放回原槽。DSM 被 Synology Assistant 发现，状态 `Ready`，黄色 STATUS 灯蜂鸣；LAN 的 5000 返回前端跳转代码，5001 TLS 握手成功且后来 HTTP 200；SMB 的 445 可建立 TCP 连接，SSH 22 未监听。

随后 DSM 成功登录，存储管理器显示 **SHR `Degraded`，而非 `Crashed`**，File Station 能浏览并打开照片。当前 CPU 使用约 **7%**，内存约 **59%**，截图无持续增长迹象；这些仅是采样，不能凭截图证明长期没有 OOM。DSM 安全顾问显示大量密码猜测事件，即使“安全检查良好”也不能否认攻击尝试。

## 第五阶段：阵列恢复（操作已启动，不声称最终完成）

通过 DSM 官方「修复」功能，将原离线的硬盘 B 用作修复目标。用户报告**修复任务已经启动**；当时未取得修复完成、两盘一致性检查和最终健康截图。因此本案例不能写成“RAID 重建成功验收完毕”。旧成员盘参加 Repair 时，目标盘旧数据将被覆盖；不能再作为独立旧备份。另请参阅 [操作手册](runbook.zh-CN.md) 的危险操作边界。

## 六个可迁移教训

1. DSM 登录故障与 Btrfs 损坏、RAID Events 差异是不同问题。
2. 独立保留一块成员盘能保留回退空间；不会因为“SMART PASSED”就免除读取故障风险。
3. 先验证一张 JPEG 和一个真实视频，再按 root 分批导出，避免直接全量冒险。
4. `EXIT_CODE=0`、源盘路径可读和真实文件完整是三个不同层次的结论。
5. 大量公网失败登录、认证进程与 OOM 的时间关联很强，但成功入侵与唯一因果关系仍需进一步证据。
6. RAID Repair 不等于备份；在修复前先确认真正不可替代的数据已有独立副本。
